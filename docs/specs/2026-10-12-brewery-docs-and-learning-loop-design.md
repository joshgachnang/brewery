# Brewery docs layout and learning loop — design

Status: approved direction
Date: 2026-10-12
Destination: the brewery repo (today `brewery/` + `dot_claude/skills/{distill,cut,barrel,finish}` in dotfiles)

## Goals

1. Record durable **decisions** somewhere that outlives a single plan.
2. Record **work as it happens** so runs can be reviewed and improved later.
3. Keep **IPs / task lists** where they already are.
4. One layout for distill → cut → sign-off → barrel → finish, instead of today's split
   between `.terreno/pipeline/<slug>.json` (vendored skills) and `.terreno/brewery/<slug>/` (CLI).
5. A **nightly** job that reads the prior day's runs and proposes improvements.
6. **CI failures** become learnings, and recurring ones get promoted into rules and skills.

## What exists today (survey, 2026-10-12)

- brewery already logs every step: `.terreno/brewery/<slug>/{state.json,context.md,steps/NNN-<stage>[-<task>]-<agent>.{prompt.md,log,result.json}}`,
  plus a global index at `~/.local/state/brewery/runs.json`. All of it is git-ignored and nothing reads it after the run.
- IPs: `docs/plans/YYYY-MM-DD-<slug>.md`, with `Status:` owned by brewery and a `## Decisions` section.
- `finish` polls `gh pr checks`, and the names and links of failing checks go into the Taste prompt. Nothing is persisted.
- `factory-retro` (Avotoast) has the only working lessons loop: `docs/factory/LESSONS.md`, with ~15 active lessons
  injected into every subagent, plus Retired and Proposals sections.
- `docs/features/` (FD system) is scaffolded but empty.
- No CI in this repo, and no scheduled Claude jobs anywhere.

## Prior art

**Every's Compound Engineering** (MIT, v3.30, very active): borrow ideas, don't install. Its `lfg`/`babysit-pr`
overlap barrel/finish almost completely. Worth taking:
- `docs/solutions/<category>/<slug>.md` with grep-able frontmatter (`problem_type`, `module`, `symptoms`,
  `root_cause`, `tags`, `retire_when`).
- The "would a future engineer still repeat this?" bar, which allows **at most one learning per run**; often the answer is "skipped".
- Updating an existing learning in preference to adding a duplicate, plus a periodic refresh that retires stale ones.
- A learnings-researcher pass during planning.
- Only a one-line pointer in CLAUDE.md, never the lessons themselves.
- Gap: CE does **not** compound CI-fix diagnoses, because its compound step runs before the PR. We should.

**claude-smart** (ReflexioAI, Apache-2.0, pre-1.0): don't install.
- Learnings live in a local SQLite DB, injected through hooks. Nothing lands in git or skills.
- It deliberately ignores headless `claude -p` runs, so it would never see a brewery run.
- It captures full transcripts globally with little redaction, and its cross-project rollups could carry PHI
  details into unrelated repos.
- Worth taking: user corrections are the strongest signal; archive superseded rules rather than delete them;
  dedupe near-duplicates.

**Conclusion:** build it into brewery. Learning runs as a **batch over durable artifacts** (brewery step files,
CI logs, merged PRs on GitHub), not over live hooks. That also covers remote, web and Cursor-cloud sessions,
because their PRs and CI runs land on GitHub regardless of where the agent ran.

## Layout (per target repo)

```
docs/
  decisions/NNNN-<slug>.md          durable decisions (ADR-lite); committed
  specs/YYYY-MM-DD-<slug>-design.md design specs (unchanged)
  plans/YYYY-MM-DD-<slug>.md        IP + task list (unchanged; Status line + ## Decisions + ## Tasks)
  journal/YYYY-MM-DD-<slug>.md      one per brewery run; generated, committed with the PR
  learnings/<category>/<slug>.md    CE-style learnings with frontmatter; committed
  learnings/RULES.md                capped active rules (~15) injected into agents; Retired + Proposals sections
.terreno/brewery/<slug>/            raw run state, unchanged, still git-ignored
  ci/NNN-<check>.json               NEW: persisted CI failure evidence
```

Rules:
- **Plans stay plans.** `## Decisions` in an IP covers that plan. A decision that should outlive the plan
  (architecture, conventions, "we don't use X") is promoted to `docs/decisions/` by finish or the nightly job, and the IP links to it.
- **The journal is generated by code, not written by an agent.**
  - At finish, brewery renders `state.json` + `steps/*.result.json` + `ci/*.json` into markdown:
    timeline, gates and human answers, Roast fails and retries, CI failures and their fixes, durations and agents used.
  - It is committed on the PR branch, so it gets reviewed with the code.
  - This is the "review later and improve" record.
- **Learnings follow CE's schema** plus `source: ci | roast | human | review` and `promoted_to:` (a rule or skill path),
  so the nightly job can see what it already did.
- **`RULES.md` replaces factory-retro's `LESSONS.md`**, generalised. Distill, cut, barrel and finish prompts include it.
- `docs/features/` (FD) is retired.
- `.terreno/pipeline/<slug>.json` is written by brewery as a projection of `state.json`, so zerg and the upstream readers keep working.

## Promotion ladder

```
observation  →  learning            →  rule                     →  skill / check
(journal,       (docs/learnings/,      (learnings/RULES.md, or     (edit SKILL.md in brewery repo,
 ci/*.json)      1 per run max)         AGENTS.md line)             or a lint/hook/test that makes it impossible)
```

- When to promote a learning to a rule: it recurs (≥2 runs), **or** the human corrected an agent once.
- When to promote a rule to a skill or check: the rule is mechanical (lint, format, type, a missing env var).
  Prefer a deterministic check in Roast over prose.
- Repo-specific lessons stay in that repo. Only **generic** lessons go up to the brewery repo's skills,
  and only after review (see PHI below).
- `RULES.md` is capped. To add a rule over the cap, retire one (moved to Retired, with the reason).

## CI capture (the gap CE leaves)

Deterministic code in `finish.ts`, with no agent involved:
1. On a red snapshot, before Taste runs, write `.terreno/brewery/<slug>/ci/NNN-<check>.json`:
   check name, run URL, head sha, and a tail of `gh run view --log-failed` (capped, scrubbed).
2. After Taste fixes it and checks go green, record the fixing commit sha in that file.
3. Classify cheaply: rerun-passed → `flaky`; otherwise leave it for the nightly job.

The pairs of "this failure, this fix" are the main input to the nightly job.

## Nightly job: `brewery cellar <repo>`

Brewery-themed name. It takes one repo (`owner/name`) per call; the host and schedule are configured outside brewery (cron or a timer, one line per repo). The `cellar` skill takes the same argument for manual runs.

Inputs for the given repo since its last cellar run:
- `runs.json` → that repo's runs: journal, `ci/*.json`, Roast FAIL reasons, human answers in `context.md`.
- `gh` for that repo: merged PRs and failed workflow runs, **including non-brewery PRs**
  (remote, web or Cursor-cloud sessions). This is how those sessions are covered without hooks.
- The current `docs/learnings/`, `RULES.md` and the brewery skills.

Steps:
1. **Cluster** CI failures and corrections by signature (check, error line, module). Ignore `flaky`, but count them
   and propose a quarantine once one check flakes N times.
2. **Write or update learnings** (CE bar, dedupe against existing ones).
3. **Promote** per the ladder; **retire** rules whose `retire_when` holds or that haven't fired in N days.
4. **Open one PR per repo** with the changes (never push to main), plus one PR to the brewery repo for skill edits.
   Use an ntfy ping, like sign-off.
5. Append a summary to `~/.local/state/brewery/cellar.log`.

Guardrails:
- At most 3 rule or skill changes per repo per night.
- It must cite the evidence (run slug, CI URL) for every change.
- It never touches the Flourish repos without review (see below).

## PHI / HIPAA

- Never read raw `~/.claude/projects/*.jsonl` transcripts. Only use brewery artifacts and GitHub data,
  which are already scoped to what agents wrote into repos and CI.
- Scrub CI log tails (emails, phone numbers, MRN-like IDs, tokens) before persisting them, and cap them at ~4KB.
- Per-repo `.brewery.json`: `learn: "off" | "local" | "shared"`. Flourish repos default to `local`:
  learnings stay in that repo and are never generalised into shared skills automatically.

## Moving to the brewery repo

Build it here first, then split it out (decided 2026-10-12). Keep everything under `brewery/` and the stage skills,
so the move stays mechanical:
- `brewery/` → repo root.
- `dot_claude/skills/{distill,cut,barrel,finish,terreno-shared,cellar}` → `skills/`.
- A `bin/install` links `~/bin/brewery` and `~/.claude/skills/*` (the zerg pattern). History moves via `git filter-repo`.

## Decisions (2026-10-12)

1. **Repo:** build in dotfiles now and move to the brewery repo afterwards.
2. **State:** `.terreno/brewery/<slug>/` stays the source of truth. brewery also writes `.terreno/pipeline/<slug>.json`
   as a projection that conforms to `terreno-shared/execution-state.schema.json`.
3. **FD system:** retire `docs/features/` and the `/fd-*` commands. Plans and `docs/decisions/` cover it.
4. **Journal:** generated at finish and committed on the PR branch under `docs/journal/`.
